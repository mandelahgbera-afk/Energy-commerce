# Plan: quotes

Item from `docs/progress.md`: "Quotes. Versions, expiry, and an accepted quote becoming an order at its quoted price, even after prices change. Discount rules still apply. Plan step 1.5."

The plan's own words (`2026-11-01-power-store-plan.md:90,97`): a proforma with an expiry date and versions; "Open quotes keep their price until they expire". Customer-facing acceptance from a link is P2 — this item is the staff-side database layer only.

## Facts, checked today

- `i_create_order` prices line by line (trade price for installer/business customers), rounds line totals and VAT the same way, judges discounts per line against the staff limit and raises `insufficient_stock` per line — `20261101000300_selling.sql:284-380`. Acceptance reuses it wholesale, so discount rules, approvals and VAT all apply untouched.
- Doc numbers come from `i_next_doc` — a new kind `Q` slots in (`foundation.sql:137`).
- Retry/decide patterns: create-style functions take a client key with `key_reused`; decide-style functions (approve a count, decide an approval) are idempotent through a row lock and status.
- Roles: counter and accountant sell and quote (`power-store-plan.md:180`).

## Design

1. **A quote is a price promise, not money or stock.** No ledger postings, no holds. Lines store the unit price and VAT rate at quote time; totals use the same rounding as orders.
2. **Versions are rows.** `quotes.version` + `root_id`; revising the latest sent version creates version+1 with fresh lines and a fresh `Q` number. An older version cannot be accepted once a newer one exists (`quote_superseded`).
3. **Expiry:** `valid_until = shop_today() + p_valid_days` (default 7, capped at 90 — a setting-like judgement, open for the shop). Accepting or revising after expiry is refused (`quote_expired`); the customer asks afresh.
4. **Acceptance** (`accept_quote`, counter or accountant, decide-style so a retry returns the first order): locks the quote row, refuses cancelled/superseded/expired, then calls `i_create_order` with the quoted unit prices. If the price has moved so the quoted price is now a bigger discount than the staff limit, the order simply carries `needs_approval` like any discounted order — the rule survives.
5. **No stock is held for quotes.** Acceptance reserves stock like any order and can fail `insufficient_stock` honestly.
6. **RLS:** quotes and lines readable by counter and accountant (owner passes); no cost columns anywhere.

## What the second reader found

No breaks across ten attacks: acceptance cannot slip past the discount gate (any quoted price below the current list by more than the accepter's limit sets `needs_approval`), deactivated products and changed customer kinds are re-judged at acceptance, concurrent revise/accept serialize on the quote row (both versions can never be accepted), insufficient stock rolls the whole acceptance back with nothing reserved and no number burned, and no Q or INV number is ever burned on a retry or failure.

One consequence to note for the shop: the discount limit judged at acceptance is the **accepter's** limit, so a counter with a 0% limit can quote 30% off and a colleague with a bigger limit can accept it — the same as the colleague typing the order fresh. If the owner wants approval at quote time instead, that's a decision for later; nothing leaks or breaks today.

## Pre-mortem: likely failures and their guards

- **Price moves between quote and accept** → order at quoted price, approval if the drop now exceeds the limit. Scene proves both directions.
- **Two counters accept one quote at once** → one order (row lock). Race scene.
- **Accept racing a revise** → revise takes a share of the quote row, so it serializes with the accept; whichever loses is refused. Scene.
- **A retry of creating a quote records twice** → client key with hash; same key returns the first quote, different lines raise `key_reused`. Scene.
